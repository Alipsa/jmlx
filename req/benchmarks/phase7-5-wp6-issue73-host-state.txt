variables shape the CPU submission pattern, not the GPU utilization.

--- review clarification (added after the session; not a new observation) ---

The ~100% duty statement above was inferred from the queue/work size, not
measured GPU utilization. The CPU sleep did not guarantee a GPU idle phase.
These runs used the original burner loop, now selected with
BURN_DRAIN_BEFORE_SLEEP=0; the current default drains before sleeping and
must not be used to reproduce these historical settings implicitly.

The per-run lines are pre-run snapshots, not continuous monitoring. The
15:49 process list is session context, not a per-run process inventory.
The session-start snapshot cannot establish the state of each of the four
clean-phase runs; those observations were not captured and cannot be
reconstructed. There is also no original-window host-state record, so the
induced compute load cannot establish which contention mix existed then.
