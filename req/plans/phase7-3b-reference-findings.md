## 4. Processor and preprocessing reference

### 4.1 Construction (2026-10-08 decision (a) in force)

Both reference tools construct the processor **directly** (no `AutoProcessor`): the slow
`Qwen2VLImageProcessor` plus `Qwen2TokenizerFast`, with explicit options. The artifacts declare
`Qwen2VLImageProcessorFast`; using the slow PIL implementation is the documented deviation. The
probe wrapper also constructs a `Qwen3VLVideoProcessor` instance via `from_pretrained` *without*
torchvision — this is only to satisfy the processor constructor's non-None `video_processor`
argument (`video_processor=None` is rejected: `TypeError: Received a NoneType for argument
video_processor, but a BaseVideoProcessor was expected`). Without torchvision, 4.57.6 resolves
`BaseVideoProcessor` to a dummy class, so the probe overrides
`check_argument_for_proper_class` for `video_processor` only; image-only behavior is unaffected.

### 4.2 The 4.57.6 slow-processor `size` bug (probed; golden `processor.slow_size_bug`)

`Qwen2VLImageProcessor.__init__` overwrites a valid `size` dict from the config with the
**defaults** `min_pixels = 3136` (56·56) and `max_pixels = 1,003,520` (14·14·4·1280), ignoring
the artifact's declared `size` {shortest_edge 65,536, longest_edge 16,777,216}
(`config_size_ignored: true` in the golden). Both reference tools therefore compensate:
`from_pretrained(dir, min_pixels=65536, max_pixels=16777216)`. The retained (inert) resolved
size dict on the slow path is `{shortest_edge: 3136, longest_edge: 1003520}`. The **planned**
jmlx path is unaffected by this bug: it reads the preprocessor JSON directly and applies the
2026-10-08 effective values (min 65,536, effective max 1,048,576 per decision (b)).

### 4.3 Resolved options (effective for the image path)

`do_resize` true, `resample` BICUBIC, `do_rescale` true with factor 1/255, `do_normalize` true

### 4.4 Color path (raw PIL → RGB float)

- `convert_to_rgb` = PIL `convert("RGB")`. **Alpha is dropped, never composited**: an RGBA or
  LA image keeps its color channels and loses its alpha. Verified with fixture
  `rgba_8x8.png`: drop-alpha matches the reference, compositing over white does not
  (`drop_alpha matches true, composite_over_white matches false`; LA same).
- **tRNS is never applied** even for palette images. Verified with a palette PNG carrying tRNS
  [0, 128, 200, 255]: the reference output matches plain `convert("RGB")` with the tRNS entry
  dropped (`drop_trns_convert_rgb matches true`).
- **EXIF orientation is applied**: the reference pipeline runs `exif_transpose` before
  resize. Verified with an orientation-6 fixture (90° CW transpose matches; no transpose does
  not). That divergence from jmlx-vision's `ImageDecoder` is closed: the WP9 policy (decided
  2026-10-16, delivered in WP2 part 1) added `ExifOrientationPolicy`, under which the Qwen3-VL
  file path decodes with `APPLY` while the SmolVLM/Idefics3 decode keeps `IGNORE` — its
  unchanged byte-for-byte contract. Since 2026-10-18 (WP2 part 2) the Qwen-path parity is
  oracle-pinned: the `qwen3vl` family's rotated cases (orientations 6 and 2, eXIf-chunk PNGs,
  §4.8) verify the slow processor's file-to-processor pipeline against jmlx's decode(`APPLY`)
  + process byte-for-byte, with an EXIF-ignoring pipeline asserted NOT to match. One
  refinement of that evidence: in 4.57.6 the slow processor's `exif_transpose` runs only on
  the string-input load path (PIL-image inputs skip it), and the WP1 exif golden above was
  measured through that path pipeline (§4.8).
- jmlx-vision's `ImageDecoder` drops the tRNS chunk before decode in all cases (existing
  behavior, retained).

### 4.5 Resize geometry — `smart_resize` (4.57.6, transcribed verbatim)

`factor = patch_size · merge_size = 32`; all arithmetic is binary64 (Python float):

```python
if max(height, width) / min(height, width) > 200: raise ValueError   # aspect guard
h_bar = round(height / factor) * factor          # note: Python `round` = banker's rounding
w_bar = round(width / factor) * factor
if h_bar * w_bar > max_pixels:
    beta = math.sqrt(height * width / max_pixels)
    h_bar = max(factor, math.floor(height / beta / factor) * factor)   # two sequential divisions
    w_bar = max(factor, math.floor(width / beta / factor) * factor)
elif h_bar * w_bar < min_pixels:
    beta = math.sqrt(min_pixels / (height * width))
    h_bar = math.ceil(height * beta / factor) * factor
    w_bar = math.ceil(width * beta / factor) * factor
```

Probe cross-check: `grid_matches_rederived_smart_resize: True` — the processor's reported
`grid_thw` for both pinned cases equals a from-scratch re-implementation of the above.

- **Division-order waiver record (2026-10-18).** The plan §4 clause asked for "a hash-pinned
  boundary fixture sensitive to division order, recording reference binary64 intermediates and
  final geometry". No such fixture exists within the default decode limits: the committed probe
  `tools/image-oracle/qwen3vl_division_order_sweep.py` sweeps the full
  `ImageDecodeLimits.DEFAULTS` range (sides ≤ 16,384, area ≤ 16,777,216; 56,380,384
  cells reaching the max-pixels branch), comparing the port's two sequential divisions
  `height / beta / factor` with the folded form `height / (beta * factor)`, and found no
  sensitive cell. The control variant `height * (1 / beta) / factor` flags 1,334 of the same
  cells, demonstrating that the sweep detects order differences (non-vacuous); the spot check
  1920x1080 → 1344x768 matches the venv-verified case. The first recorded evidence was a
  narrower venv sweep of [2, 4000)^2 (12,087,517 cells reaching the max-pixels branch) plus the
  squares in [1000, 20000) step 16, now subsumed by the wider sweep; its ranges and conclusion
  remain in the comment above the 160x6560 max-pixels case in
  `Qwen3VlGeometryPlanTest` (`jmlx-vision`), whose venv-verified geometry cases — including
  that max-branch case — re-run under the ordinary `:jmlx-vision:test` task. Callers may pass
  larger `ImageDecodeLimits`, so a division-order-sensitive input remains unproven beyond the
  defaults; the clause is waived on this evidence within that scope. The boundary fixtures
  instead record final geometry and digests.

### 4.6 Normalization, temporal duplication, patch permutation

- **Order and dtype:** uint8 RGB → resize (BICUBIC) → `× 1/255` → `(x − 0.5) / 0.5`, all in
  float32. Output tensor shape `[num_patches, 3 · 2 · 16 · 16]` = `[N, 1536]`.
- **Temporal duplication:** one image is one frame; it is repeated to 2 identical frames so
  `grid_t = 2 / temporal_patch_size = 1`. Both temporal slots of every patch hold identical
  pixel data.
- **Flatten order** (row-major over these axes): `(t, merged_h, merged_w, merge_h, merge_w,
  c, temporal, patch_row, patch_col)` — i.e. the patch grid grouped into merge blocks, block
  major; innermost axis order `(c, temporal, patch_row, patch_col)` → 1536 = 3·2·16·16. The
  4.57.6 source does this as `reshape` + `transpose(0, 3, 6, 4, 7, 2, 1, 5, 8)`. This ordering
  is load-bearing for the merger and the vision rotary positions (§5, §6).
- **AlphaPolicy (new, additive, `jmlx-vision`):** the reference's `convert("RGB")` semantics are
  "drop alpha, keep source color channels." The existing `ImageDecoder` default
  (`COMPOSITE_OVER_WHITE`, the Pillow-exact integer composite) served 7.3a and is unchanged for
  every existing overload; the new enum value `DROP_ALPHA` implements the reference semantics
  for the Qwen3-VL file→processor path. tRNS is stripped before decode under **both** policies.
  New `ImageDecoder.decode(Path|InputStream, limits, policy)` overloads; `null` policy rejected
  (test). Verified by the §4.4 fixtures and `:jmlx-vision` tests (RGBA/LA drop-vs-composite).

## 5. Vision tower arithmetic (transformers 4.57.6, `modeling_qwen3_vl.py`)

All shapes below for the 2B; the 8B analogue is in §8.4. N = `grid_t · grid_h · grid_w`.

1. **PatchEmbed:** `nn.Conv3d(3, 1024, kernel=[2,16,16], stride=[2,16,16], bias=True)` over the
   view `(-1, 3, 2, 16, 16)` of the flattened patches → `[N, 1024]`
   (checkpoint weight [1024, 3, 2, 16, 16]).
2. **Learned position embedding + interpolation:** `pos_embed` is a learned table
   `[2304, 1024]` = 48×48 grid (`num_position_embeddings` 2304, `num_grid_per_side` 48).
   `fast_pos_embed_interpolate` samples it bilinearly for a (h, w) grid: indices
   `torch.linspace(0, 47, h)` / `linspace(0, 47, w)` (binary64), floor/ceil with ceil clipped
   to 47, weights = fractional parts; result is permuted into the **same merge-block order**
   as the patches (§4.6) and **added** to the patch-embed output. Probed:
   `pos_embed_interpolated` `[N, 1024]`.
3. **Blocks × `depth` (24 for 2B):** pre-norm
   `LayerNorm(1024, eps 1e-6, bias)` → attention → residual; `LayerNorm` → MLP
   (`linear_fc1` 1024→4096 **bias** → `gelu_pytorch_tanh` → `linear_fc2` 4096→1024 **bias**)
   → residual. At each `deepstack_visual_indexes` block (2B: 5, 11, 17) the block's **post
   MLP+residual** output is also routed to the merger list (deepstack, §6.6).
4. **Vision attention:** a single fused `qkv` `Linear(1024 → 3·16·128, bias)`; 16 heads of
   head_dim 64, **no GQA**; **non-causal** full attention over each image, segmented per image
   via `cu_seqlens` (eager/sdpa path: split + per-segment attention; FA2 path: `cu_seqlens`
   passthrough); softmax **upcast to float32**; `o_proj` `Linear(2048 → 1024, bias)`.
5. **Vision rotary (two-axis):** `Qwen3VLVisionRotaryEmbedding(head_dim // 2 = 32, theta
   10000)`. `rot_pos_emb(grid_thw)` assigns each patch a **(row, col) index pair in the
   processor's merge-block order** (merge block major, then the 2×2 in-block position) and
   builds `freqs = cat(row_inv, col_inv)` → `[N, 32]`; `cos/sin = cat((freqs, freqs), -1)` →
   `[N, 64]`. `apply_rotary_pos_emb_vision` upcasts q, k to float32, applies
   `q·cos + rotate_half(q)·sin`, casts back to the input dtype. Probed: `rot_pos_emb`
   `[N, 32]` for both cases.
6. **Merger (final):** the block output, still in merge-block order, is reshaped
   `(…, 2, 2, hidden)` → `LayerNorm(eps 1e-6)` (main merger: `use_postshuffle_norm False` —
   the norm is applied **before** the 2×2 grouping) → `linear_fc1` (1024→4096, bias) →
   `nn.GELU()` (**plain GELU, not the tanh approximation**) → `linear_fc2` (4096→2048, bias)
   → `[merged_rows, 2048]`, `merged_rows = N / 4`. The 2×2 grouping comes from the input
   ordering (the processor's permutation §4.6 + the pos-embed interpolation's permute), not
   from a shuffle inside the merger. Probed: `merger_out` [64, 2048] / [72, 2048].
7. **Deepstack mergers:** `deepstack_merger_list` — 3 `PatchMerger`s for the 2B
   (`use_postshuffle_norm True`, i.e. the norm placement differs from the main merger), each
   producing `[merged_rows, 2048]` from the hidden states captured at blocks 5/11/17; these
   three feature tensors are forwarded to the text side (§6.6). Probed: 3× [64, 2048] /
   [72, 2048].
8. **Biases:** every vision linear has a bias (qkv, o_proj, fc1, fc2, patch_embed); text-side
   attention has none (`attention_bias false`). Consistent with the checkpoint tensor
   inventory in both artifacts.

**Per-case intermediates (2B, probed, golden `vision`):**

| case | N | `pos_embed_interpolated` | `rot_pos_emb` | `patch_embed/block0/block_last` | `merger` | `deepstack` |
|---|---:|---|---|---|---|---|
| 256×256 | 256 | [256, 1024] | [256, 32] | [256, 1024] ×3 | [64, 2048] | 3× [64, 2048] |
| 64×32 | 288 | [288, 1024] | [288, 32] | [288, 1024] ×3 | [72, 2048] | 3× [72, 2048] |

### 6.4 MRoPE delta and cache positions

`delta = llm_positions.max() + 1 − len(input_ids)` (`processing_qwen3_vl.py:1011`) — the
negative amount by which the *logical* sequence index exceeds the largest *position value*:

- 256×256: `11max → 25 + 1 − 82 = −56` (= merged-grid max dim 8 − token count 64, algebraically
  equivalent for a single image)
- 64×32: `15max → 16 + 1 − 90 = −60` (= 12 − 72)

**Cache vs. RoPE positions are different counters** (probed decode, 4 steps each):

| case | HF `cache_position` | KV length | RoPE positions (all axes equal after image) |
|---|---|---|---|
| 256×256 | 82, 83, 84, 85 | 83…86 | 26, 27, 28, 29 |
| 64×32 | 90, 91, 92, 93 | 91…94 | 30, 31, 32, 33 |

jmlx must keep these separate: the KV cache slot advances by 1 per token, while the RoPE
position follows the three-axis max + 1 (which coincide with the sequential index only because
the image block's T axis saturates at `st_idx`).

### 6.5 Interleaved MRoPE layout (text decoder)

`mrope_interleaved: true` with `mrope_section [24, 20, 20]` (sum 64 = head_dim/2) and
`rope_theta` 5,000,000. Transcribed from the 4.57.6 source
(`modular_qwen3_vl.py:409-444`, `Qwen3VLTextRotaryEmbedding`):

1. `freqs` is built per axis: for d ∈ {0=T, 1=H, 2=W},
   `freqs[d] = position_ids[d] @ inv_freq` in **float32** (autocast explicitly disabled),
   giving `(3, bs, seq, 64)`.
2. `apply_interleaved_mrope(freqs, mrope_section)` starts from the **T row** and overwrites
   in place:
   ```python
   freqs_t = freqs[0]                                  # T owns every frequency initially
   for dim, offset in enumerate((1, 2), start=1):      # H, then W
       length = mrope_section[dim] * 3                 # 60 for both
       idx = slice(offset, length, 3)
       freqs_t[..., idx] = freqs[dim, ..., idx]
   ```
   i.e. H writes frequency indices `1, 4, 7, …, 58` (20 frequencies) and W writes
   `2, 5, 8, …, 59` (20); everything else stays T (24). Final per-frequency owner for f ∈
   0..63: `f % 3 == 0 → T`, `f % 3 == 1 → H` (f < 60), `f % 3 == 2 → W` (f < 60), and
   `f ∈ 60..63 → T` — a T-starting round-robin `T H W T H W …` with a terminal run of four T
   frequencies (the source docstring: chunked `[TTT…HHH…WWW]` → interleaved
   `[THTHWHTHW…TT]`).
3. `emb = cat((freqs_t, freqs_t), -1)` → 128; `cos = emb.cos() · attention_scaling`,
   `sin = emb.sin() · attention_scaling` (scaling = 1.0 for `rope_type: default`), computed in
   float32 and cast back to the input dtype before use in the attention rotate-half op.

### 6.6 DeepStack timing (text side)

**Compute/cast order (frozen; transcribed from §6.5).**

1. Per-axis float32 frequencies: for d ∈ {0=T, 1=H, 2=W},
   `freqs[d][t, i] = float32(positions[d][t]) · invFreq[i]` — the position ids cast to
   float32 (exact for the non-negative coordinates) and a single float32 multiply per
   frequency, a length-1 reduction, exact. `invFreq[i] = 1 / theta^(2i/rotaryDims)` is
   derived once at construction (pinned reference: `theta = 5,000,000`,
   `rotaryDims = 2·Σ mrope_section = 128`, `Σ = 64 = head_dim/2`).
2. Interleaved overwrite starting from the T row (a per-frequency owner selection, bit-
   identical to the reference's in-place overwrite): for dim 1 (H) `length =
   mrope_section[1]·3` and `idx = slice(1, length, 3)` — H owns frequency indices
   `1, 4, 7, …, 1+3(s1−1)` (count s1); for dim 2 (W) `length = mrope_section[2]·3` and
   `idx = slice(2, length, 3)` — W owns `2, 5, 8, …, 2+3(s2−1)` (count s2); everything else
   stays T (owner(f) = T when `f % 3 == 0` or `f >= 3·(s1+s2)`). Pinned reference
   `[24,20,20]`: H owns `1, 4, …, 58` (20 frequencies), W owns `2, 5, …, 59` (20), T owns
   the remaining 24 — a T-starting round-robin `T H W T H W …` with a terminal run of four
   T frequencies. The implementation realizes the selection with a static owner table: a
   single byte array of length `rotaryDims/2` holding one 0/1/2 owner (T/H/W) per frequency
   slot, derived from the sections at construction (the H and W conditions are disjoint, so
   every slot has exactly one owner) selects, per (token, frequency) on the CPU before any
   array is written, the owned row's position — the same copy the mask expression
   `freqsT·wT + freqsH·wH + freqsW·wW` is a bit-identical copy of for non-negative finite
   frequencies (multiply by 1.0/0.0 and add in float32 are exact there) — so each `freqs_t`
   element is still exactly one float32 multiply of the same two operands (owned position ·
   `invFreq[i]`) using only the existing facades.
3. `emb = cat((freqs_t, freqs_t), −1)` → per token `[rotaryDims]` (128 pinned, = head_dim).
4. `cos = cos(emb) · attention_scaling`, `sin = sin(emb) · attention_scaling`, computed in
   float32; `attention_scaling = 1.0` for `rope_type: default` (the pinned artifact), so
   the multiply is the identity on finite float32 values and is omitted.
5. Cast cos/sin to the input array's dtype (a no-op for the FLOAT32 model; kept for dtype
   correctness of the composition).
6. In the input dtype, `out = x·cos + rotate_half(x)·sin`, where `rotate_half` is the NeoX
   half-split form `(−x2, x1)`: `cat((−x[…, n:], x[…, :n]), −1)` — the same layout the fast
   kernels use with `traditional=false`. Only the `rotaryDims` prefix of each head is
   rotated; the tail `[rotaryDims, headDim)` passes through unchanged (partial rotary).

**Frozen signatures.**

New core components in `se.alipsa.jmlx.nn` — a dedicated component, **not** a new
`RopeSpec` variant: the sealed `RopeSpec` hierarchy gains no permitted variant, preserving
source compatibility for exhaustive consumer switches (plan §6).

- `public final class MultiAxisRope` — immutable; holds theta, the cloned sections and the
  derived `rotaryDims`/`invFreq`/owner masks. Deliberately not a `Module`: no parameters,
  no children, no owned scope; every MLX array it builds allocates into the caller's scope.
  ```java
  public MultiAxisRope(float theta, int[] mropeSection)
  public float theta()
  public int[] mropeSection()     // defensive copy
  public int rotaryDims()         // 2 · Σ mropeSection
  public MultiAxisRotation prepare(MLXScope scope, int batch, int sequence, int[][] positions)
  ```
  `positions` is `int[3][batch·sequence]` — three rows of length B·T (row-major flattened
  `[B,T]`), row 0 = T (time), row 1 = H (height), row 2 = W (width). Chosen over three
  separate `int[]` parameters: it is the reference's `[3, B·T]` `position_ids` layout as
  one validated object, its row order is the `mrope_section` order and the §6.5 axis
  indices 0/1/2, and `Qwen3VlPromptPlan`'s `temporalPositions()`/`heightPositions()`/
  `widthPositions()` map to the rows one-to-one in that order. Validation, all
  `IllegalArgumentException`, all checked **before any MLX array is written**: constructor —
  theta finite and positive (the `RopeSpec` convention), sections non-null (cloned), every
  element ≥ 0, Σ ≥ 1 (rotaryDims is even by construction); `prepare` — batch ≥ 1, sequence ≥
  1, exactly 3 rows, each row's length == batch·sequence (computed in `long` with overflow
  checked before use), and no negative coordinate (rejected). Frequencies/cos/sin are
  computed on every `prepare` call: no position-derived state is cached. The computation
  follows the frozen order: one `[B·T, rotaryDims/2]` float32 position matrix (the
  owner-mask-selected row per frequency, built directly from the int rows — the exact
  cast) × the `[1, rotaryDims/2]` `invFreq` array by a single broadcast multiply →
  `freqs_t` (bit-identical to the per-axis ×-then-owner-mask selection, step 2);
  concatenate → `emb`; `MLXOps.cos`/`MLXOps.sin` in `scope` → FLOAT32 arrays reshaped to
  `[batch, 1, sequence, rotaryDims]` (broadcastable over the heads axis). Host-memory trade-off
  (accepted in review): the one position-matrix upload now holds `B·T·rotaryDims/2` float32 values
  on the host where the pre-restructure path held `3·B·T` (three per-axis position arrays) — about 21× more for
  the pinned 2B at a 32k prefill (8 MB vs 384 KB) — while decode (`B·T = 1`) is strictly cheaper
  and the prefill cost is small next to the prefill compute.
- `public final class MultiAxisRotation` — the per-step rotation state one `prepare`
  produces and every layer of that step shares, computed once per step and threaded exactly
  like the existing per-step `stepFrequencies`:
  ```java
  public MLXArray cos()     // FLOAT32 [batch, 1, sequence, rotaryDims]
  public MLXArray sin()     // FLOAT32 [batch, 1, sequence, rotaryDims]
  public int rotaryDims()
  public MLXArray rotate(MLXArray x)    // x: [batch, heads, sequence, headDim]
  ```
  `rotate` casts cos/sin to `x.dtype()` (frozen step 5), rotates the `rotaryDims` prefix
  (frozen step 6) and concatenates the untouched tail back; it validates `x`'s rank/shape
  against the stored cos/sin shape and `rotaryDims ≤ headDim` (the head-dimension
  validation) before building anything.

  ```
- **Masked residual add** (DeepStack level i: add `features_i [1, F_i, hidden]` into the
  `[1, L, hidden]` hidden states at exactly the image-token rows, zero elsewhere):
  ```
  zeroRow = MLX.zeros(scope, {1, 1, hidden}, hidden.dtype())        // [1, 1, hidden]
  source  = concatenate([zeroRow, features_i], 1)                   // [1, 1 + F_i, hidden]
  gather  = gatherIndices(L, destinations_i) remapped: i -> 0, L + f -> 1 + f   // int[L]
  mask    = takeAxis(source, MLXArray(gather, [L]), 1)
  updated = MLXOps.add(hidden, mask)
  ```
  The gather indices are the shared `mergeGatherIndices` helper's output (the same
  one the row-gather replacement above applies directly) remapped over the source's
  `1 + F_i` rows — every identity row (shared index `i < L`) remaps to the zero row
  (source index `0`), the `f`-th destination (shared index `L + f`, strictly
  increasing) remaps to source row `1 + f` — which is what lets the zero pad be a
  single `[1, 1, hidden]` row instead of a full `[1, L, hidden]` zero tensor. The
  caller `scope`'s relatedness to the operands' scopes (one an ancestor of the
  other) is validated before any MLX array is written. The add matches the
  reference's masked clone + add + write-back (§6.6) and leaves every non-image

class Qwen3VLVisionModel(Qwen3VLPreTrainedModel):
    config: Qwen3VLVisionConfig
    _no_split_modules = ["Qwen3VLVisionBlock"]

        super().__init__(config, *inputs, **kwargs)
        self.spatial_merge_size = config.spatial_merge_size
        self.patch_size = config.patch_size
        self.spatial_merge_unit = self.spatial_merge_size * self.spatial_merge_size

        self.patch_embed = Qwen3VLVisionPatchEmbed(
            config=config,
        )

        self.pos_embed = nn.Embedding(config.num_position_embeddings, config.hidden_size)
        self.num_grid_per_side = int(config.num_position_embeddings**0.5)

        head_dim = config.hidden_size // config.num_heads
        self.rotary_pos_emb = Qwen3VLVisionRotaryEmbedding(head_dim // 2)

        self.blocks = nn.ModuleList([Qwen3VLVisionBlock(config) for _ in range(config.depth)])
        self.merger = Qwen3VLVisionPatchMerger(
            config=config,
            use_postshuffle_norm=False,
        )

        self.deepstack_merger_list = nn.ModuleList(

                    use_postshuffle_norm=True,
                )
                for _ in range(len(config.deepstack_visual_indexes))
            ]
        )

    def rot_pos_emb(self, grid_thw: torch.Tensor) -> torch.Tensor:
        merge_size = self.spatial_merge_size

        max_hw = int(grid_thw[:, 1:].max().item())
        freq_table = self.rotary_pos_emb(max_hw)  # (max_hw, dim // 2)
        device = freq_table.device

        total_tokens = int(torch.prod(grid_thw, dim=1).sum().item())
        pos_ids = torch.empty((total_tokens, 2), dtype=torch.long, device=device)

        offset = 0
        for num_frames, height, width in grid_thw:
            merged_h, merged_w = height // merge_size, width // merge_size

            block_rows = torch.arange(merged_h, device=device)  # block row indices
            block_cols = torch.arange(merged_w, device=device)  # block col indices
            intra_row = torch.arange(merge_size, device=device)  # intra-block row offsets
            intra_col = torch.arange(merge_size, device=device)  # intra-block col offsets

            # Compute full-resolution positions
            row_idx = block_rows[:, None, None, None] * merge_size + intra_row[None, None, :, None]
            col_idx = block_cols[None, :, None, None] * merge_size + intra_col[None, None, None, :]

            row_idx = row_idx.expand(merged_h, merged_w, merge_size, merge_size).reshape(-1)
            col_idx = col_idx.expand(merged_h, merged_w, merge_size, merge_size).reshape(-1)

            coords = torch.stack((row_idx, col_idx), dim=-1)

            if num_frames > 1:
                coords = coords.repeat(num_frames, 1)

            num_tokens = coords.shape[0]
            pos_ids[offset : offset + num_tokens] = coords
            offset += num_tokens

        embeddings = freq_table[pos_ids]  # lookup rotary embeddings
        embeddings = embeddings.flatten(1)
        return embeddings

    def fast_pos_embed_interpolate(self, grid_thw):
        grid_ts, grid_hs, grid_ws = grid_thw[:, 0], grid_thw[:, 1], grid_thw[:, 2]

        idx_list = [[] for _ in range(4)]
        weight_list = [[] for _ in range(4)]

        for t, h, w in zip(grid_ts, grid_hs, grid_ws):
            h_idxs = torch.linspace(0, self.num_grid_per_side - 1, h)
            w_idxs = torch.linspace(0, self.num_grid_per_side - 1, w)

            h_idxs_floor = h_idxs.int()
            w_idxs_floor = w_idxs.int()
            h_idxs_ceil = (h_idxs.int() + 1).clip(max=self.num_grid_per_side - 1)
            w_idxs_ceil = (w_idxs.int() + 1).clip(max=self.num_grid_per_side - 1)

            dh = h_idxs - h_idxs_floor
            dw = w_idxs - w_idxs_floor

            base_h = h_idxs_floor * self.num_grid_per_side
            base_h_ceil = h_idxs_ceil * self.num_grid_per_side

            indices = [
                (base_h[None].T + w_idxs_floor[None]).flatten(),
                (base_h[None].T + w_idxs_ceil[None]).flatten(),
                (base_h_ceil[None].T + w_idxs_floor[None]).flatten(),
                (base_h_ceil[None].T + w_idxs_ceil[None]).flatten(),
            ]

            weights = [
                ((1 - dh)[None].T * (1 - dw)[None]).flatten(),
                ((1 - dh)[None].T * dw[None]).flatten(),
                (dh[None].T * (1 - dw)[None]).flatten(),
                (dh[None].T * dw[None]).flatten(),
            ]

            for i in range(4):
                idx_list[i].extend(indices[i].tolist())
                weight_list[i].extend(weights[i].tolist())

        idx_tensor = torch.tensor(idx_list, dtype=torch.long, device=self.pos_embed.weight.device)
        weight_tensor = torch.tensor(
            weight_list, dtype=self.pos_embed.weight.dtype, device=self.pos_embed.weight.device
        )
        pos_embeds = self.pos_embed(idx_tensor) * weight_tensor[:, :, None]
        patch_pos_embeds = pos_embeds[0] + pos_embeds[1] + pos_embeds[2] + pos_embeds[3]

        patch_pos_embeds = patch_pos_embeds.split([h * w for h, w in zip(grid_hs, grid_ws)])

        patch_pos_embeds_permute = []
        merge_size = self.config.spatial_merge_size
        for pos_embed, t, h, w in zip(patch_pos_embeds, grid_ts, grid_hs, grid_ws):
            pos_embed = pos_embed.repeat(t, 1)
            pos_embed = (
                pos_embed.view(t, h // merge_size, merge_size, w // merge_size, merge_size, -1)
                .permute(0, 1, 3, 2, 4, 5)
                .flatten(0, 4)
            )
            patch_pos_embeds_permute.append(pos_embed)
        patch_pos_embeds = torch.cat(patch_pos_embeds_permute)
        return patch_pos_embeds

    def forward(self, hidden_states: torch.Tensor, grid_thw: torch.Tensor, **kwargs) -> torch.Tensor:
        """
        Args:
            hidden_states (`torch.Tensor` of shape `(seq_len, hidden_size)`):
                The final hidden states of the model.
            grid_thw (`torch.Tensor` of shape `(num_images_or_videos, 3)`):
                The temporal, height and width of feature shape of each image in LLM.

        Returns:
            `torch.Tensor`: hidden_states.
        """
        hidden_states = self.patch_embed(hidden_states)

        pos_embeds = self.fast_pos_embed_interpolate(grid_thw)
        hidden_states = hidden_states + pos_embeds

        rotary_pos_emb = self.rot_pos_emb(grid_thw)

        seq_len, _ = hidden_states.size()
        hidden_states = hidden_states.reshape(seq_len, -1)
        rotary_pos_emb = rotary_pos_emb.reshape(seq_len, -1)
        emb = torch.cat((rotary_pos_emb, rotary_pos_emb), dim=-1)
        position_embeddings = (emb.cos(), emb.sin())

        cu_seqlens = torch.repeat_interleave(grid_thw[:, 1] * grid_thw[:, 2], grid_thw[:, 0]).cumsum(
            dim=0,
            # Select dtype based on the following factors:
            #  - FA2 requires that cu_seqlens_q must have dtype int32
            #  - torch.onnx.export requires that cu_seqlens_q must have same dtype as grid_thw
            # See https://github.com/huggingface/transformers/pull/34852 for more information
            dtype=grid_thw.dtype if torch.jit.is_tracing() else torch.int32,
        )
        cu_seqlens = F.pad(cu_seqlens, (1, 0), value=0)

        deepstack_feature_lists = []
        for layer_num, blk in enumerate(self.blocks):
            hidden_states = blk(
                hidden_states,
                cu_seqlens=cu_seqlens,
                position_embeddings=position_embeddings,
                **kwargs,
            )
            if layer_num in self.deepstack_visual_indexes:
                deepstack_feature = self.deepstack_merger_list[self.deepstack_visual_indexes.index(layer_num)](
                    hidden_states
                )
                deepstack_feature_lists.append(deepstack_feature)

        hidden_states = self.merger(hidden_states)

        return hidden_states, deepstack_feature_lists

class Qwen3VLVisionAttention(nn.Module):
    def __init__(self, config: Qwen3VLVisionConfig) -> None:
        super().__init__()
        self.dim = config.hidden_size
        self.num_heads = config.num_heads
        self.head_dim = self.dim // self.num_heads
        self.num_key_value_groups = 1  # needed for eager attention
        self.qkv = nn.Linear(self.dim, self.dim * 3, bias=True)
        self.proj = nn.Linear(self.dim, self.dim)
        self.scaling = self.head_dim**-0.5
        self.config = config
        self.attention_dropout = 0.0
        self.is_causal = False

    def forward(
        self,
        hidden_states: torch.Tensor,
        cu_seqlens: torch.Tensor,
        rotary_pos_emb: Optional[torch.Tensor] = None,
        position_embeddings: Optional[tuple[torch.Tensor, torch.Tensor]] = None,
        **kwargs,
    ) -> torch.Tensor:
        seq_length = hidden_states.shape[0]
        query_states, key_states, value_states = (
            self.qkv(hidden_states).reshape(seq_length, 3, self.num_heads, -1).permute(1, 0, 2, 3).unbind(0)
        )
        cos, sin = position_embeddings
        query_states, key_states = apply_rotary_pos_emb_vision(query_states, key_states, cos, sin)

        query_states = query_states.transpose(0, 1).unsqueeze(0)
        key_states = key_states.transpose(0, 1).unsqueeze(0)
        value_states = value_states.transpose(0, 1).unsqueeze(0)

        attention_interface: Callable = eager_attention_forward
        if self.config._attn_implementation != "eager":
            attention_interface = ALL_ATTENTION_FUNCTIONS[self.config._attn_implementation]

        if self.config._attn_implementation == "flash_attention_2":
            # Flash Attention 2: Use cu_seqlens for variable length attention
            max_seqlen = (cu_seqlens[1:] - cu_seqlens[:-1]).max()
            attn_output, _ = attention_interface(
                self,
                query_states,
                key_states,
                value_states,
                attention_mask=None,
                scaling=self.scaling,
                dropout=0.0 if not self.training else self.attention_dropout,
                cu_seq_lens_q=cu_seqlens,
                cu_seq_lens_k=cu_seqlens,
                max_length_q=max_seqlen,
                max_length_k=max_seqlen,
                is_causal=False,
                **kwargs,
            )
        else:
            # Other implementations: Process each chunk separately
            lengths = cu_seqlens[1:] - cu_seqlens[:-1]
            splits = [
                torch.split(tensor, lengths.tolist(), dim=2) for tensor in (query_states, key_states, value_states)
            ]

            attn_outputs = [
                attention_interface(
                    self,
                    q,
                    k,
                    v,
                    attention_mask=None,
                    scaling=self.scaling,
                    dropout=0.0 if not self.training else self.attention_dropout,
                    is_causal=False,
                    **kwargs,
                )[0]
                for q, k, v in zip(*splits)
            ]
            attn_output = torch.cat(attn_outputs, dim=1)

        attn_output = attn_output.reshape(seq_length, -1).contiguous()
        attn_output = self.proj(attn_output)
        return attn_output
```

```python
def apply_rotary_pos_emb_vision(
    q: torch.Tensor, k: torch.Tensor, cos: torch.Tensor, sin: torch.Tensor
) -> tuple[torch.Tensor, torch.Tensor]:
    orig_q_dtype = q.dtype
    orig_k_dtype = k.dtype
    q, k = q.float(), k.float()
    cos, sin = cos.unsqueeze(-2).float(), sin.unsqueeze(-2).float()
    q_embed = (q * cos) + (rotate_half(q) * sin)
    k_embed = (k * cos) + (rotate_half(k) * sin)
    q_embed = q_embed.to(orig_q_dtype)
    k_embed = k_embed.to(orig_k_dtype)
    return q_embed, k_embed
```

### 11.2 Design decisions

**Per-image sequential execution.** jmlx processes one image at a time with one unmasked
noncausal `MLXFast.scaledDotProductAttention` per image, instead of the reference's packed
rows split per image by `cu_seqlens`. Numerically identical: attention mixes nothing across
images, and every other op in the tower (RoPE, norms, MLP, merger) is row-wise, so packing
versus looping changes only the scheduling of independent row computations, not their
values. Looping also bounds the concurrent attention workspace to a single image (plan §4
budget).

**Patch projection: core `Conv3d` adopted.** The tower uses the core `Conv3d` (native mlx
conv3d), with the weight transposed from PyTorch OIHW to jmlx channels-last
`[out, kt, kh, kw, in]` via axes [0,4,1,2,3] in the HF-provenance weight map. The
flattened-linear alternative (reshape the 5-D weight into a 2-D GEMM over the 1,536-wide
patch rows) is recorded as rejected in favor of the native conv path; the strict evidence
for the choice is the golden's `patch_embed` comparison
(`Qwen3VlVisionTowerGoldenTest`, WU5), which validates the chosen conv output against the
reference. The MLX/mlx-vlm channels-last checkpoint provenance plan is deferred to WP6's
affine scope.

**Learned-position interpolation.** Frozen candidate: double linspace
`v_i = ((side - 1.0) / (n - 1)) * i` for i in 0..n-1 with `side` = `num_grid_per_side`; the
WU2 golden probes pin the exact torch double bits for n ∈ {4, 6, 8}, side 8, and WU3's
pure-Java test asserts bit-equality — if the candidate does not bit-match, this section
gets an addendum naming the expression that does. Floor by int truncation; ceil = floor+1
clipped to `side - 1`; the double fractions are rounded to float32 when the weight vector
is built, matching the reference's `torch.tensor(weight_list, dtype=…)` which casts the
doubles to the table dtype at tensor creation; the four corner rows are combined as a
float32 bilinear sum. The merge-block ordering is applied directly: jmlx patches and the
reference's output are both in merge-block order, so no separate permute is needed.

**Vision RoPE.** `inv_freq` is computed in FLOAT32 —
`1.0 / (theta ** (arange(0, dim, 2, float32) / dim))`, theta 10000, `dim = head_dim // 2`
(16 frequencies for the 2B, head_dim 64); the WU2 golden pins the exact 16 float32 bits and
the WU3 test asserts bit-equality. Positions are the patch's actual (row, col) grid
coordinates in merge-block order (block·merge + intra). `freqs = [row_freqs | col_freqs]` →
`[N, dim]`; `emb = cat(freqs, freqs)` → `[N, head_dim]`; cos/sin in float32. The rotation
upcasts q/k to float32, computes `q·cos + rotate_half(q)·sin` in float32, and casts back to
the input dtype — the OPPOSITE compute/cast order of the WP4 `MultiAxisRotation` (which
casts cos/sin down to the input dtype and computes there); the new core `TwoAxisRotation`
documents both orders.

**Merger ordering.** The main merger (`use_postshuffle_norm False`) norms per-patch over
`hidden` BEFORE the view into merged rows; the DeepStack mergers
(`use_postshuffle_norm True`) view into merged rows FIRST and norm over `hidden·merge²`
(4096 for the 2B). Both use exact (erf) GELU — `nn.GELU()`, NOT tanh; the vision BLOCKS
use `gelu_pytorch_tanh` (`hidden_act`) for their MLP. eps 1e-6 is hardcoded in the 4.57.6
source (block norms and both merger norm placements), not a config field, so jmlx
hardwires 1e-6.

**Weights: stored bf16, run float32.** Weights are stored bf16 in the synthetic checkpoint
(as in the real 2B artifact); the tower upconverts everything to FLOAT32 at construction
(plan §7: float correctness initially computed in FLOAT32, including conversion of stored
weights). For the 2B the WP1 probe golden reports 315 bf16 `model.visual.*` tensors
totalling 813,914,112 bytes (776.21 MiB) as stored; the float32 conversion doubles that to
1,627,828,224 bytes (1,552.42 MiB, ≈1.52 GiB) for the tower's lifetime.

**Checkpoint key scheme.** The synthetic checkpoint uses the real artifact's
`model.visual.*` key scheme (WP1 probe inventory; §5 of this findings doc) — if the bare
`Qwen3VLVisionModel.save_pretrained` omits the `model.visual.` prefix, the generator adds
it back explicitly and documents the choice in the golden provenance. The tower's
public `visionWeights` map renames the checkpoint keys to its own child-tree paths; the
only structural rename is the conv weight transpose above. Every `model.visual.*` key
that does not map to a known tower key is rejected rather than skipped (PR #58 review):
a numeric block or DeepStack merger index past the configured depth or DeepStack count
is named with the limit that excludes it, and any other unrecognised visual key — an
unknown sub-key (the MLP branch maps only the `linear_fc1`/`linear_fc2` affine
`weight`/`bias`), an unknown top-level visual key, a non-numeric or overflowing index —
is named as unrecognised; only genuinely non-visual checkpoint keys are skipped. The
method is all-or-nothing (PR #58 review round 2): it maps and validates every key
before transposing or closing anything, so a thrown rejection leaves the caller's
checkpoint map byte-for-byte untouched (the conv weight is transposed and its original
closed only on success, the `SmolVlmModel` pattern).

### 11.4 Measured per-image peak

Method: `Qwen3VlVisionPeakTest` (native, ordinary `test` task) runs the real-2B tower
geometry — hidden 1024, 16 heads, head_dim 64, intermediate 4096, out_hidden 2048,
`num_position_embeddings` 2304, patch/temporal 16/2, merge 2 — at three reduced depths,
each with one DeepStack index (depth 1: index 0; depths 3 and 4: index 1), constant
0.001 weights via `MLX.full`, and one synthetic 1024×1024 image (grid (1, 64, 64), 4096
patch rows) processed through `Qwen3VlImageProcessor`. The test settles a baseline
`MLXMemory.activeBytes()` with every static array already evaluated (all three towers'
weights, bracket-attention weights, inputs, rotations), then records four tower
measurements, each one forward in a fresh per-request scope:

1. The tower forward's own per-image transient peak at depth 1 — the depth-independent
   floor: `MLXMemory.resetPeak()` right before `tower.forward(request, images)`,
   `MLXMemory.peakBytes()` right after. The forward evaluates and releases each block's
   intermediates internally (private per-block child scopes), so `peakBytes() - baseline`
   is one block's live intermediates plus the conv, the position-embedding gathers and
   the mergers, plus the 16 MiB of hoisted rows.
2. The same transient at the depth-3 proxy, which must stay under the plan §4 bound.
3. The sustained per-image evaluated peak at depth 3: a settled active-bytes delta
   (`settledAfter - baseline`) taken while the per-request scope is still open — the
   per-block and per-image scopes close inside the forward, and the hoisted merged and
   DeepStack rows live in the per-request scope until it closes, as in production.
4. The same transient at depth 4; with the depth-1 transient it bounds per-block
   accumulation (the difference must stay under 64 MiB).

plus a fifth bracket, the transient per-image attention workspace: a direct single
`TwoAxisRotaryAttention` forward at 4096 rows (q/k/v [4096, 16, 64], constant weights),
bracketed by `resetPeak()` before and `peakBytes()` after the evaluated forward, run
after every per-request scope closes so the bracket peak carries no retained-row offset.
The depth-3 transient, the depth-3 sustained peak and the attention bracket are asserted
against the plan §4 5 GiB planning bound; the depth-1/depth-4 pair is asserted against
the 64 MiB depth-independence bound.

Measured (M5 Max, ordinary `test` task, MLX_ENABLE_TF32=1 default, 2026-10-23, per-block
evaluate-and-release in place):

- Tower forward per-image transient peak (depth-3 proxy): **1,606,025,248 B ≈ 1.50 GiB
  (1,531.63 MiB)** over the settled baseline — 2,483,028,048 B (≈2.31 GiB) below the
  pre-fix depth-3 peak of 4,089,053,296 B, which carried every block's intermediates
  live at once.
- Sustained per-image evaluated peak: **16,777,216 B — exactly 16 MiB**. This is precisely the
  logical retained output of the tower on the 4096-row image after the per-block and
  per-image scopes close: the merged 1024-row × 2048-float `out_hidden` representation
  plus one DeepStack level (1024 × 2048 floats), i.e. 2 × 1024 × 2048 × 4 B = 16 MiB —
  the merged rows and the `[1]` deepstack capture, nothing else retained. Unchanged by
  the per-request-scope review fix: the retained rows now live in the caller's per-request
  scope instead of the tower's module scope, but the single-image forward concatenates
  nothing, so the same 16 MiB is retained until the per-request scope closes.
- Transient attention workspace (bracketed by the direct `TwoAxisRotaryAttention` forward at
  4096 rows): **335,544,320 B = exactly 320 MiB (0.3125 GiB)** — unchanged by the per-block
  fix, which never touches a single-attention call. Exactly five single-head 4096×4096
  float32 matrices (67,108,864 B each); the full 16-head score matrix is
  1,073,741,824 B = 1 GiB. In the isolated call MLX's fused scaled-dot-product kernel
  tiles the score computation and never materializes the full matrix, which is why the
  measured transient is well under even one full matrix. The bracket runs after every
  per-request scope closes, so the 16 MiB of retained rows no longer offsets the bracket
  peak.
- Depth sweep with the per-block fix in place (same probe, 2026-10-23): depth 1 =
  **1,757,020,216 B (1.64 GiB)**, depth 3 = **1,606,025,248 B (1.50 GiB)**, depth 4 =
  **1,606,025,248 B (1.50 GiB)** — the depth-3 and depth-4 transients are bit-for-bit
  equal, and depth 4 − depth 1 = **−150,994,968 B (−144.00 MiB)**. The per-image peak no
  longer scales with depth. The depth-1 transient being slightly *higher* than the
  depth-3/4 ones is the allocator's pool floor on a shorter allocation sequence, not
  accumulation — which is why the test's bound is one-sided: it fails only if depth 4
  exceeds depth 1 by more than 64 MiB, the signature of per-block accumulation returning.

Depth scaling — cause, decomposition, and the fix. The pre-fix peak **was** depth-dependent
(pre-fix sweep, 2026-10-23: depths 1–4 gave 1,908,015,184 B, 2,914,648,160 B,
4,089,053,296 B and 5,263,458,432 B; per-block slope exactly **1,174,405,136 B ≈ 1.09 GiB**
in both measured intervals; extrapolated to the real depth of 24: 28,751,561,152 B ≈
26.8 GiB ≈ 5.4× the bound — the concern that motivated the fix). The slope was not an
attention score-matrix story; the following is an inference from arithmetic and code
reading, not a profiler trace:

- Cause: every block's ops resolved their result arrays into the one per-image scope, so
  the Java `MLXArray` handles for every intermediate of every block stayed live until the
  per-image scope closed at the end of the image — each block added its intermediates to
  the peak instead of releasing them.
- Decomposition: **1,174,405,136 B = 70 × 16 MiB + 16 B**, where 16 MiB is one
  [4096, 1024] float32 row buffer (4096 patch rows × 1024 hidden × 4 B) — 70 pinned
  [4096, 1024]-sized intermediate row-units per block plus 16 B of overhead. Reading the
  block's op sequence gives ≈73 such row-units (the norm outputs, the [4096, 3072] qkv
  row-unit and its q/k/v splits, the rotary-rotated q/k, the attention output and
  projection, the two residual adds, and the 4096-wide MLP intermediates at 4 row-units
  each), so the measured 70 and the read ≈73 agree within the attention-tiled workspaces
  that never materialize full [4096, 1024] rows.
- The 320 MiB isolated-attention bracket (= exactly 20 row-units, matching the ≈20–23
  attention row-units in the decomposition) refutes the alternative kept-score-matrix
  theory: one 16-head float32 score matrix would be 1,073,741,824 B = 1 GiB, and the
  fused SDPA kernel tiles it — the bracket peaks at 20–23 row-units' worth, never a full
  matrix.
- Fix (this review round): `runImage` now wraps each block in a private per-block child
  scope of the image scope — the block's entry row is pinned into it (same-shape
  `broadcastTo`, the `T5Model.project` idiom), the block's output and (when tapped)
  DeepStack rows are evaluated and hoisted out, and the block scope closes before the
  next block starts, so one block's intermediates are released before the next
  accumulate. The computation is bit-identical to the pre-change graph — uncompiled MLX
  does not fuse across eval boundaries — verified exact-bits in both TF32 modes against
  the pre-change recording (`exactBitsVerifyVision`, 6 captures × 20,971,520 floats
  each, `build/exact-bits/wp5-vision/tf32-{1,0}/`, recorded at 0dc7595).

The flagged concern is now a regression test: `Qwen3VlVisionPeakTest` asserts
peak(4) − peak(1) < 67,108,864 B (64 MiB) in addition to the plan §4 bound on the
depth-3 proxy, so a returning per-block accumulation fails the ordinary `test` task
rather than waiting for a full-depth run. `Idefics3VisionTower` (the
`SmolVlmModel`'s tower) shares the same per-request-scope pattern without per-block
scopes and may scale the same way; it is out of scope for this fix.

Planning bound (plan §4): below the 5 GiB bound — at 4096 rows and 16 heads one FLOAT32
score matrix is 1 GiB, and the budget conservatively allows four such matrices (4 GiB)
plus Q/K/V and block/merger activations. The depth-3 tower-forward proxy (1.50 GiB), the
16 MiB sustained and the 0.31 GiB attention bracket all pass under it. Since the
per-image peak is now depth-independent (depth 3 and 4 bit-for-bit equal, asserted),
the bound applies to the full depth-24 tower's per-image transient as well — the
pre-fix ≈26.8 GiB extrapolation no longer holds. Not a claim that the model fits a
7 GB host.

### 11.5 Linspace probes at the real 2B geometry (2026-10-23, PR #58 review round 2)

The original bit probes pinned only `torch.linspace(0, 7, n)` for the tiny tower's
side 8, n ∈ {4, 6, 8}. The real 2B model uses `num_position_embeddings` 2304 (side
48), and the 4096-row grid-64×64 peak case reaches n up to 64 per axis (§11.4), so
the kernel's larger-n branch at side 48 was unpinned. Review round 2 suspected
torch's CPU `linspace_kernel` might switch formulas at the SIMD vector width for
large n (a `Vectorized::arange` path), which would make the scalar port 1 ulp off
at the real geometry and shift the bilinear weights and floor indices. The
generator now also pins `torch.linspace(0, 47, n)` for n ∈ {16, 24, 32, 50, 64}
(186 values): n = 64 is the grid-64×64 cap, n = 50 is odd so the kernel's
`i < n / 2` split is pinned at a non-power-of-two. Storage: appended to
`probes.linspace` in the existing per-entry shape with an explicit `"side"` field;
the side-8 entries keep their original shape (no `"side"`), so the golden diff is
purely additive. Regeneration: the checkpoint and all four images are
byte-identical (probes are computed after the reference forward and draw no RNG),
so only the golden digest was re-pinned in `provenance.json`.

Outcome: **no Java change needed.** `Qwen3VlVisionTower.linspaceValue` (the exact
torch 2.6.0 CPU `linspace_kernel` port: float32 step = the float32 rounding of the
double `(end - start) / (n - 1)`; each value the float32 rounding of `start +
(double) step * i` for `i < n / 2` and `end - (double) step * (n - i - 1)`
otherwise) bit-matches all five new probes as-is. The golden test
(`linspaceProbesBitMatchPinnedTorch`, which reads each probe's `"side"` with the
config-derived side 8 as default) now asserts all eight entries — 202 values at
float32 bit level — and is green (float32GoldenTest 50/0, the suite 3/3).

Why the vectorized-path hypothesis is wrong for this pin: torch v2.6.0's
`linspace_kernel` (`aten/src/ATen/native/cpu/RangeFactoriesKernel.cpp` @ v2.6.0)
calls `cpu_serial_kernel` — the vectorized lambda was removed upstream ("Remove
vectorization implementation, due to the precision issue between integer and
double"), and the `Vectorized::arange` vector path exists only in `arange_kernel`,
not `linspace_kernel`. The scalar half-way split is therefore the formula at every
n. Confirmed empirically in the pinned venv (torch 2.6.0+cpu): a sweep of
n ∈ [2, 512] at side {8, 47, 48, 4096} produces **zero** bit differences between
`torch.linspace(0, side - 1, n)` and the Java formula, all five pinned geometries
included. No formula switch at any vector width, so the port stays bit-exact at
the real 2B's n = 64 and the floor index/weight consumers are pinned. Because no
Java output changed, the `build/exact-bits/wp5-vision/` baselines are untouched
and `exactBitsVerifyVision` stays bit-identical in both TF32 modes. Host note:
the original captures and these five entries were pinned on the same host
(`platform` Darwin-arm64 in the golden's provenance block); in any case the
scalar kernel above computes the values from bit-exact float arithmetic, so
they are host-independent.
