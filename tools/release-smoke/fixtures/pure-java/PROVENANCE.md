# Release-smoke pure-Java fixtures: provenance

This fixture set drives the `pure-java` release-smoke profile (`tools/release-smoke/run.sh
ci|candidate|central --profile pure-java`). It is packaging/integration data only: hand-computed
and pinned-oracle values, not a new model artifact and not a replacement for the tokenizer or
image differential oracles. Every digest is recorded in `digests.txt` (recompute with
`shasum -a 256` from this directory; the two `../..`-prefixed entries are resolved from the
repository's `tools/` directory).

## Resize case

One case from the image oracle's committed resize family:

- Case name: `small-96x64-oddup-101x73-bilinear` (input 96x64, output 101x73, resample code 2).
- `resize-case.json` carries the case's `image`, `width`, `height` and `resample` fields, copied
  verbatim from the matching `cases[]` entry of
  `tools/image-oracle/fixtures/resize.input.json`.
- `resize-small-96x64.png` is a byte copy of
  `tools/image-oracle/fixtures/resize/small-96x64.png`. Both files are SHA-256-pinned in
  `tools/image-oracle/provenance.json` under `/fixtureSources/resize.input.json` (key for the
  input spec) and `/fixtureSources/resize/small-96x64.png` (key for the image):
  `239db3b3c3a936b3494e21402c04b7edf944a06d2278e41a690125cdb8870ab6` and
  `71bcf8f79e3f08afa3c1ce67ec974866170211b6849673d26faf36c92f54989c`.
- `resize.expected.json` (the case's `pixelsBase64` source) is **not** digest-pinned in the
  image oracle's provenance. Its own SHA-256,
  `1406c672319464b8314e4eab65517ffd37b15e6c0d403e7f3d4f717dba55a338`, is therefore recorded
  here and in `digests.txt`. Its reference authority is the pinned Python
  `verifyImageOracleFixtures` run (hash-locked `tools/image-oracle/.venv`), not root `check`.
  A reviewed `generateImageOracleFixtures` run that changes that expected file requires updating
  `resize-expected.bin` and this recorded digest in the same change, then rerunning both oracle
  verification and the pure smoke.
- `resize-expected.bin` is the case's base64-decoded `pixelsBase64` value, byte-for-byte
  (22119 bytes = 101 x 73 x 3, row-major RGB, no padding):
  `05a55c7b286304d83ec1479c4368fa9cc8d8d47b4c5e118f9c4d690fd3e4cad7`.
- These Pillow-recorded bytes are the resize reference; they were generated by the pinned
  Pillow 12.3.0, not hand-computed or Java-generated. The Pillow port provenance (ported source
  files, SHA-256s, MIT-CMU license) is pinned in `jmlx-vision/NOTICE`, which the smoke asserts
  is present in the published vision jars.
- The consumer maps the Pillow integer codes explicitly: `1` → `Resampling.LANCZOS`,
  `2` → `Resampling.BILINEAR`, `3` → `Resampling.BICUBIC`; any other code is rejected rather
  than treated as a Java enum ordinal.

The consumer also normalizes a simple 2x2 input analytically (no oracle file): for each pixel
channel `p`, `((float)(p * scale) - mean[c]) / std[c]`, asserted as exact float32 values in an
`ImageTensor` of shape `[1, h, w, 3]` and `Layout.NHWC`.

## Tokenizer

`tokenizer/tokenizer.json` is a **hand-written** minimal byte-level BPE tokenizer (not
Hugging Face-generated and not derived from the full smoke's Mistral pair, which is checkpoint-
specific). It was cross-verified against the pinned HF `tokenizers==0.23.2`
(`tools/tokenizer-oracle/.venv`) for the exact encode/decode facts below, and its incremental
span behavior matches `jmlx-tokenizer`'s `RuntimeIncrementalDecoder` UTF-8 hold-back semantics:

- `encode("héllo world")` (no special tokens) = `[3, 4, 5, 32, 7, 8, 9, 7, 33, 11]`,
  tokens `h`, `Ã`, `©`, `ll`, `o`, `Ġ`, `w`, `o`, `rl`, `d`.
- Full decode round-trips to `héllo world`; with `skipSpecialTokens=true` the result is
  unchanged (no special ids occur).
- Incremental decoding: `é` spans the byte tokens `Ã` (id 4, byte `0xC3`) and `©` (id 5, byte
  `0xA9`); `append(4)` emits `""` (incomplete UTF-8 held back), `append(5)` emits `é`, and the
  combined deltas equal the full decode.
- The vocabulary deliberately avoids bytes where the HF 0.23.2 byte-fallback table and
  `jmlx-tokenizer`'s table disagree (for example `0xF6` → `¶` in HF vs. `ö` in jmlx); `é`
  (`0xC3`, `0xA9`) is printable under both.
- The `post_processor` is ByteLevel-only on purpose: the pinned HF `tokenizers` 0.23.2 cannot
  parse a `Sequence` post-processor containing `TemplateProcessing`, so a minimal parseable
  shape keeps the fixture verifiable against the independent reference.

`tokenizer/tokenizer_config.json` carries a chat template designed to be **engine-agnostic**:
single-line, with every newline written as a `{{ '\n' }}` escape so that HF transformers
rendering (`trim_blocks=True, lstrip_blocks=True`) and `jmlx-jinja` rendering produce identical
output despite differing default whitespace policies. It observes the clock through
`strftime_now('%Y-%m-%dT%H:%M')`, using only the directive set pinned in `jmlx-jinja`'s
`PosixStrftime` (`%Y %m %d %b %B %H %M %%`), which the consumer pins with a fixed UTC clock
(`2026-11-04T12:00:00Z`). For the messages `system: "be brief"`, `user: "héllo world"` and
`add_generation_prompt=true`, the exact rendered prompt is:

```
system: be brief
user: héllo world
assistant:
at 2026-11-04T12:00
```

(trailing newline included). The prompt's exact token ids are asserted by the consumer; the
template text itself was cross-verified with the pinned transformers 4.57.6
(`tools/image-oracle/.venv`) rendering with the same pinned clock.

No Hub credentials, model downloads or remote code are needed to consume this fixture set.
