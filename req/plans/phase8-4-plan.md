# Phase 8.4 — First native release

Date: 2026-11-14. Status: accepted; tooling implementation in progress; publication not started.
Current evidence and open prerequisites: [readiness checklist](../phase8-4-release-checklist.md).

Parent: [Full roadmap, Phase 8](../full-roadmap.md#phase-8--first-releases-and-framework-adapters).
Phase 8.3 merged in [PR #94](https://github.com/Alipsa/jmlx/pull/94), merge commit
`679d525b43d33eba552af3e6c4f46d80ee6ec673`. Its
[implementation report](../phase8-3-implementation-report.md) records local validation;
WP0 records hosted acceptance evidence separately. Creating this plan does not authorize
Central publication or claim that the release gates have passed.

## 1. Goal and boundaries

Publish the native runtime, FFM/core/models chain and both framework adapters in one combined
Central deployment. Reuse unchanged pure-Java artifacts from 8.1, release changed ones, and
prove the complete nine-module graph through independent Maven consumers before and after
publication. Phase 8 ends only after Central verification and the development-version bump.

This milestone changes release tooling, native build configuration, version declarations and
release documentation. Pinning the deployment target and removing build-machine paths change
the native binary bytes without changing upstream pins; rebuild and reverify those bytes.
It adds no inference features, model families, framework integrations or performance
optimizations. Preserve native pins, generated bindings, numerical goldens, precision modes
and the existing native ownership rules. Any correctness fix discovered during verification
must receive its own review and invalidate affected candidate evidence.

The [8.2 benchmark](../phase8-2-benchmark.md#8-handoff-to-84--what-the-first-native-release-may-state)
and dated scope amendment carried by 8.3 bound release claims. Accepted evidence limitations
remain limitations; publication must not turn unstable, blocked or unmatched measurements
into passed performance gates. Phase 9.1 owns optimization follow-up.

and unknown, and the candidate's normal JDK. If no usable historical version can be established
or provisioned, select a new version. Bound discovery to these evidence sources; do not turn
missing vendor provenance into an open-ended investigation or an automatic three-module bump.

Initial inspection finds changes in shared build logic/catalog and module build files since
8.1. This plan therefore does not predeclare the pure-Java modules unchanged. WP0 produces

and the reuse/new-version rationale. Changed publication contracts require new coordinates.
A new jinja version also requires a new tokenizer publication carrying that dependency edge.

Restore reused modules to their published versions before generating release POMs. Keep the
entire approved release tuple checked out through candidate verification, deployment and
Central verification. Do not republish reused coordinates. New dependency edges must contain
release versions: jinja → tokenizer, ffi → core → models, tokenizer/vision → models,
models → both adapters. The native jar is a separate runtime dependency; do not introduce a
published core-to-native dependency. One combined bundle satisfies new internal edges without
individual deployment ordering.
